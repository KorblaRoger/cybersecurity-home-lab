======================================================================

During Ubuntu-side testing, UBUNTU01 attempted to ping the Windows
VMnet2 adapter:

Source:      10.10.10.40
Destination: 10.10.10.1

The initial test resulted in:

4 packets transmitted, 0 received, 100% packet loss.

Additional Ubuntu-side testing demonstrated that:

- UBUNTU01 had the correct static IPv4 address: 10.10.10.40/24.
- A directly connected route existed for 10.10.10.0/24.
- Ubuntu selected ens33 when routing traffic to 10.10.10.1.
- Ubuntu successfully resolved 10.10.10.1 to MAC address
  [REDACTED].
- The learned MAC address matched the Windows VMnet2 adapter.
- Windows successfully pinged UBUNTU01 at 10.10.10.40.

These results indicated that VMnet2 connectivity, IPv4 addressing,
routing, and Layer 2 neighbor resolution were functioning.

The investigation therefore proceeded to Windows host-side
configuration and firewall behavior.

11. ROOT CAUSE AND RESOLUTION
======================================================================

Problem:

UBUNTU01 could not initially ping the Windows VMnet2 adapter at
10.10.10.1 even though both systems were configured on the
10.10.10.0/24 subnet.

Evidence:

- Windows VMnet2 address was correctly configured as 10.10.10.1/24.
- UBUNTU01 was correctly configured as 10.10.10.40/24.
- Both systems successfully resolved each other's MAC addresses.
- Windows successfully pinged UBUNTU01.
- Ubuntu correctly selected its directly connected route for
  10.10.10.1.
- Windows built-in inbound ICMPv4 Echo Request rules were disabled.

Root Cause:

Inbound ICMPv4 Echo Requests to the Windows host were not permitted
by the applicable Windows Firewall configuration.

Resolution:

Created the following dedicated lab firewall rule:

Cyber Lab - Allow ICMPv4 from VMnet2

The rule permits inbound ICMPv4 Echo Requests from:

10.10.10.0/24

Validation:

After applying the rule, UBUNTU01 successfully pinged the Windows
VMnet2 adapter with 0% packet loss.


======================================================================
12. SECURITY AND TROUBLESHOOTING LESSONS
======================================================================

1. A failed ping does not by itself prove that a network path is
   unavailable.

2. IP addressing, routing, ARP resolution, and host firewall behavior
   should be investigated separately.

3. Bidirectional ARP resolution demonstrated that Layer 2
   communication was functioning even while one direction of ICMP
   testing failed.

4. Reverse-direction testing helped isolate the problem.

5. Host-based firewalls can produce asymmetric connectivity behavior.

6. Windows Firewall did not need to be disabled to solve the problem.

7. A least-privilege firewall rule was preferable to broadly enabling
   ICMP access.

8. Restricting the rule to 10.10.10.0/24 limited the permitted
   traffic to the dedicated cybersecurity lab network.
