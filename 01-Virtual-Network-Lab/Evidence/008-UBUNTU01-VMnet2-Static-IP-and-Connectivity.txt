======================================================================
OBJECTIVE
======================================================================

The objective of this stage was to manually configure UBUNTU01 with
a static IPv4 address after moving the virtual machine from VMware
VMnet8 NAT to the isolated VMnet2 host-only network.

VMnet2 was intentionally configured without VMware DHCP and NAT.

The experiment was designed to demonstrate that:

1. A host can be manually assigned an IPv4 address without DHCP.
2. Hosts on the same IPv4 subnet can communicate directly without
   a default gateway.
3. A default gateway is required to reach networks outside the
   directly connected subnet.
4. DNS is not required when communicating directly by IP address.
5. Host firewall rules can affect connectivity even when addressing,
   routing, and Layer 2 communication are functioning correctly.

receive an IPv4 address.

The detailed unconfigured state was captured separately in:

Observation:

A default gateway and DNS server were intentionally omitted so that
local-subnet connectivity could be tested independently from routing
and name resolution.

Observation:

UBUNTU01 had a valid IPv4 address and directly connected route for

The failed ping was not treated as proof that VMnet2 itself was

======================================================================
11. WINDOWS FIREWALL INVESTIGATION
======================================================================

Windows Firewall was investigated rather than disabled.

The built-in File and Printer Sharing ICMPv4 inbound Echo Request
rules were found to be disabled.

This explained why:

Windows -> UBUNTU01 ping succeeded

while:

UBUNTU01 -> Windows ping failed

A narrowly scoped Windows Firewall rule was created to permit inbound
ICMPv4 Echo Requests originating from the VMnet2 lab subnet:

10.10.10.0/24

Firewall rule name:

Cyber Lab - Allow ICMPv4 from VMnet2

Security decision:

Windows Firewall was NOT disabled.

Instead, only the traffic required for the lab was permitted from the
specific 10.10.10.0/24 lab subnet.

13. EXTERNAL IPV4 CONNECTIVITY TEST
======================================================================

Command:

ping -c 4 8.8.8.8

Output:

ping: connect: Network is unreachable

Result:

FAILED AS EXPECTED.

Observation:

This was an intentional and expected failure.

The routing table contained a route for:

10.10.10.0/24

8.8.8.8 is outside the directly connected 10.10.10.0/24 subnet.

Because UBUNTU01 had no default gateway, Linux had no route indicating
where packets destined for 8.8.8.8 should be sent.

This demonstrated the difference between:

Local-subnet communication:
10.10.10.40 -> 10.10.10.1 = SUCCESS

Remote-network communication:
10.10.10.40 -> 8.8.8.8 = NETWORK UNREACHABLE

======================================================================
15. ROOT CAUSE AND RESOLUTION OF FAILED PING
======================================================================

Problem:

After assigning UBUNTU01 the static address 10.10.10.40/24, an
initial ping from Ubuntu to the Windows VMnet2 adapter at 10.10.10.1
resulted in 100% packet loss.

Troubleshooting:

- Verified ens33 was UP.
- Verified UBUNTU01 had 10.10.10.40/24.
- Verified the 10.10.10.0/24 directly connected route.
- Verified the route selected for 10.10.10.1.
- Verified ARP/neighbor resolution for 10.10.10.1.
- Confirmed the learned MAC address matched the Windows VMnet2
  adapter.
- Successfully pinged UBUNTU01 from Windows.
- Inspected Windows Firewall ICMP rules.

Root Cause:

Windows was not permitting inbound ICMPv4 Echo Requests from the
VMnet2 lab network.

Resolution:

A narrowly scoped Windows Firewall rule was created to permit
inbound ICMPv4 Echo Requests from the 10.10.10.0/24 lab subnet.

Windows Firewall was not disabled.

Validation:

The ping from UBUNTU01 to 10.10.10.1 was repeated and succeeded.


======================================================================
16. SECURITY AND TROUBLESHOOTING OBSERVATIONS
======================================================================

1. A failed ping does not automatically mean the network is down.

2. Interface state, IP addressing, routing, ARP, firewall behavior,
   and application/service availability should be investigated
   separately.

3. Successful ARP resolution can demonstrate local Layer 2
   communication even when ICMP Echo Requests do not receive replies.

4. Hosts on the same IPv4 subnet communicate directly and do not
   require a default gateway.

5. A default gateway is needed when traffic must reach a network that
   is not directly connected.

6. DNS is not required when communicating directly using IP
   addresses.

7. Host firewalls can produce asymmetric test results where one host
   can ping another but the reverse ping fails.

8. Security controls should not be broadly disabled during
   troubleshooting when a narrower configuration change can solve
   the problem.

9. The Windows Firewall change followed a least-privilege approach by
   permitting ICMPv4 Echo Requests only from the dedicated
   10.10.10.0/24 lab subnet.
